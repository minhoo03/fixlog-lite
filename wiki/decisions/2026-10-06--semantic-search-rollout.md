# 의미 기반 검색의 단계적 도입

## 배경

위키는 Codex의 장기 기억을 보완하고, 이후 개인·팀 위키와 Discord 봇에서 같은 지식을 검색하기 위해 만든다. 현재 템플릿에는 실제 검색 대상 문서가 없으므로 임베딩 검색의 정확도, 지연시간과 토큰 절감 효과를 실측할 수 없다.

Codex는 로컬 저장소의 파일명과 메타데이터를 검색하고 후보 문서를 읽은 뒤, 질문과 내용의 의미적 관련성을 모델 판단으로 평가할 수 있다. 이는 사전 계산된 벡터를 사용하는 임베딩 검색과는 다른 방식이다.

## 결정

초기 단계에서는 별도 임베딩 인덱스 없이 `$wiki-search`를 사용한다.

1. 제목, `summary`, `aliases`, `tags`와 본문을 키워드 및 확장 표현으로 검색한다.
2. Codex가 관련 후보 문서를 직접 읽고 의미를 판단한다.
3. 근거 문서의 경로와 관련 제목을 답변에 표시한다.
4. 검색 결과가 약하면 다른 표현으로 재검색하되, 확인되지 않은 사실은 추측하지 않는다.

다음 조건 중 하나가 충족되면 키워드 검색과 임베딩 검색을 결합한 공용 검색 모듈을 구현한다.

- Discord 봇 구현을 시작한다.
- 개인 위키와 팀 위키 등 여러 저장소를 함께 검색한다.
- 관련 문서를 찾기 위해 반복 검색이 자주 필요하다.
- 한 질문에 너무 많은 문서를 읽어 LLM 입력 토큰이나 응답 시간이 커진다.
- 표현이 달라 관련 문서를 놓치는 사례가 확인된다.

## 구현 시 검증 기준

실제 문서와 대표 질문 모음을 사용해 직접 검색과 하이브리드 검색을 같은 조건에서 비교한다.

- 상위 5개 결과의 정답 문서 포함률
- 검색 지연시간의 중앙값과 95백분위
- 답변 모델에 전달되는 문서 토큰 수
- 질문당 검색 도구 호출 횟수
- 인덱싱 비용과 변경 문서 재색인량

검색 모듈은 변경된 문서만 다시 인덱싱하고, 생성된 벡터와 캐시는 `.wiki-cache/`에 저장해 Git에서 제외한다. Codex와 Discord 봇은 같은 검색 모듈과 결과 형식을 공유한다.

## 근거

- 현재 단계에서는 직접 검색이 별도 의존성, API 키와 인덱스 관리 없이 동작한다.
- 임베딩은 문서가 쌓이고 질의가 반복될수록 후보 문서 선별 비용과 LLM 입력 토큰을 줄인다.
- Discord 봇은 Codex의 로컬 탐색 능력을 그대로 사용할 수 없으므로 독립 검색기가 필요하다.
- 실제 데이터 없이 지금 검색 파라미터를 확정하면 정확도와 비용을 검증할 수 없다.

## 영향

- 현재 `wiki-search`는 Codex의 직접 파일 검색을 기본 경로로 사용한다.
- 임베딩 검색은 폐기한 것이 아니라 측정 가능한 시점까지 미룬다.
- Discord 봇 개발을 시작할 때 이 문서와 루트의 `SEARCH.md`를 우선 참고한다.

## 검토한 대안

- 지금 임베딩 검색기를 완성한다: 실제 검색 문서와 평가 질문이 없어 품질을 검증할 수 있으므로 보류한다.
- 임베딩을 사용하지 않는다: 팀 위키, 다중 저장소와 Discord 봇의 반복 질의에서 검색 효율과 재현성이 낮아질 수 있어 채택하지 않는다.
