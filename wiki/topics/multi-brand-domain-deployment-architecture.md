# 하나의 배포본으로 여러 브랜드 도메인 운영하기

## 핵심 요약

- 브랜드마다 별도 빌드가 꼭 필요한 것은 아니다. 같은 실행 코드가 요청의 Host를 보고 브랜드를 선택할 수 있다.
- 배포 워크플로우는 환경별 빌드와 호스팅 프로젝트 선택을 담당하고, 브랜드 도메인의 연결은 호스팅 설정에서 관리한다.
- 한 호스팅 프로젝트에 여러 커스텀 도메인이 연결돼 있으면 한 번의 운영 배포로 모든 연결 도메인이 같은 새 버전을 제공한다.
- 소스코드만으로는 DNS, TLS 인증서, 커스텀 도메인 연결 상태를 확정할 수 없다. 호스팅 대시보드와 DNS 설정을 함께 확인해야 한다.

## 예시 상황

가상의 회사 ExampleCo가 하나의 체크아웃 위젯을 `brand-a.example`과 `brand-b.example`이라는 두 브랜드로 제공한다고 가정한다. `.example`은 문서 예시에 사용하도록 예약된 도메인이므로 실제 서비스와 혼동되지 않는다.

구조의 핵심은 브랜드별로 애플리케이션을 복제하는 것이 아니라 다음 세 책임을 분리하는 데 있다.

```text
애플리케이션 코드: 요청 Host를 보고 브랜드 선택
배포 워크플로우: 환경에 맞는 빌드본을 호스팅 프로젝트에 배포
호스팅·DNS 설정: 실제 도메인을 해당 프로젝트에 연결
```

## 1. 요청 Host로 브랜드 선택

브랜드 선택은 빌드 시점이 아니라 요청 처리 시점에 할 수 있다.

```ts
const brandBDomain = "brand-b.example";
const isBrandB =
  hostname === brandBDomain || hostname.endsWith(`.${brandBDomain}`);

return isBrandB ? BRAND.B : BRAND.A;
```

이렇게 하면 `checkout.brand-b.example`이나 `preview.brand-b.example`처럼 같은 도메인 계층의 서브도메인을 하나의 규칙으로 처리할 수 있다. 빌드본은 같고 아이콘, 이름, 색상 같은 표현만 요청별로 달라진다.

단순한 `hostname.includes("brand-b")` 검사는 피한다. `brand-b.example.attacker.example` 같은 무관한 호스트도 잘못 일치할 수 있기 때문이다. 정확한 도메인과 점(`.`) 경계를 포함한 서브도메인 접미사를 검사해야 한다.

프록시나 CDN 뒤에서 동작한다면 애플리케이션이 어떤 Host 헤더를 신뢰할지도 명시해야 한다. 외부 요청이 전달 헤더를 임의로 주입하지 못하도록 신뢰할 수 있는 프록시에서 헤더를 덮어쓰거나 검증한다.

## 2. 환경별로 배포 단위를 나누기

배포 워크플로우는 대체로 다음 입력과 책임을 가진다.

```yaml
on:
  workflow_call:
    inputs:
      target:
        required: true
        type: string

jobs:
  deploy:
    steps:
      - run: build --mode "${TARGET}"
      - run: hosting-cli deploy --project "web-${TARGET}" --production
```

실제 구성에서는 환경마다 다음 항목이 달라질 수 있다.

- 체크아웃할 배포용 브랜치 또는 커밋
- 빌드 모드와 공개 환경 변수
- 배포할 호스팅 프로젝트
- 동시 배포 제어와 실패 알림

워크플로우는 어느 호스팅 프로젝트에 어떤 빌드본을 올릴지 결정한다. 어느 브랜드 도메인이 그 프로젝트를 바라보는지는 워크플로우가 아니라 호스팅과 DNS 설정의 책임이다.

## 3. 한 프로젝트에 여러 도메인 연결하기

하나의 호스팅 프로젝트에 다음처럼 여러 도메인을 연결할 수 있다.

```text
호스팅 프로젝트: web-staging
├── checkout.brand-a.example
└── checkout.brand-b.example
```

`web-staging`에 새 버전을 한 번 배포하면 두 도메인은 같은 새 배포본을 제공한다. 사용자가 어느 도메인으로 접근했는지에 따라 애플리케이션이 브랜드를 선택한다.

즉, 일반적인 흐름은 다음과 같다.

```text
코드 변경
→ 환경별 빌드
→ 환경에 대응하는 호스팅 프로젝트에 한 번 배포
→ 프로젝트에 연결된 모든 도메인이 같은 버전을 제공
→ 애플리케이션이 요청 Host를 보고 브랜드별 표현을 선택
```

브랜드마다 기능이나 릴리스 시점이 달라야 한다면 단일 배포본 구조가 맞지 않을 수 있다. 이 경우 브랜드별 프로젝트나 빌드 구성을 분리하는 편이 명확하다.

## 4. 코드만 보고 알 수 있는 것과 없는 것

### 코드에서 확인할 수 있는 것

- Host에서 브랜드를 선택하는 규칙
- 기본 브랜드와 알 수 없는 Host의 처리 방식
- 환경별 빌드 모드와 배포 대상 프로젝트를 고르는 규칙
- 브랜드별 UI 자산과 메타데이터가 요청 단위로 적용되는지 여부

### 호스팅·DNS 설정에서 확인해야 하는 것

- 각 커스텀 도메인이 실제로 어느 프로젝트에 연결돼 있는지
- DNS 레코드가 올바른 대상을 가리키는지
- TLS 인증서 발급과 갱신이 정상인지
- 운영 도메인이 운영 배포를, 테스트 도메인이 테스트 배포를 제공하는지
- 도메인 리디렉션이나 기본 도메인 정책이 의도한 대로인지

코드에 브랜드 분기 로직이 있어도 도메인이 다른 프로젝트에 연결돼 있거나 연결 자체가 빠져 있으면 원하는 화면을 제공할 수 없다. 반대로 같은 프로젝트에 연결된 두 도메인은 별도 브랜드 배포 없이도 동시에 갱신된다.

## 5. 운영 점검표

- 정확한 도메인 또는 점 경계를 포함한 서브도메인 접미사로 판별하는가?
- 알 수 없는 Host가 들어왔을 때 기본 브랜드를 보여줄지 요청을 거부할지 정했는가?
- 브랜드 선택이 지역, 언어, 배포 환경 같은 다른 개념과 섞이지 않았는가?
- 환경별 프로젝트와 도메인 연결표를 운영 문서에서 관리하는가?
- 테스트 환경의 도메인이 운영 백엔드나 운영 프로젝트를 가리키지 않는가?
- 각 브랜드 도메인에서 아이콘, 제목, 공유 이미지와 canonical URL까지 올바르게 바뀌는가?
- Host 또는 전달 Host 헤더의 신뢰 경계를 검토했는가?
- 브랜드별 독립 릴리스가 필요해질 때 프로젝트 분리 기준이 있는가?

## 기억할 점

**배포 단위, 도메인 연결, 브랜드 선택은 서로 다른 책임이다.** 한 배포본을 여러 도메인이 공유하게 만들 수 있지만, 그 사실을 보장하려면 코드뿐 아니라 호스팅 프로젝트와 DNS의 실제 연결 상태까지 확인해야 한다.
