# 웹·모바일 프론트엔드 업무를 위한 핵심 개념

> 목표: 기술의 정의뿐 아니라, 어떤 문제를 어떻게 해결하며 어디까지 해결하지 못하는지 이해한다.
> 아래의 도입 이유는 일반적인 실무 사례이며, 해당 조직의 실제 도입 배경을 단정한 것은 아니다.

## 1. pnpm + Turborepo: 코드 공유와 반복 작업 관리

**어떤 문제가 있었나?**
웹과 모바일이 검증·계산·API 코드를 복사해서 쓰면 수정이 누락되고 동작이 달라진다. 저장소를 합쳐도 모든 패키지를 매번 빌드하면 개발과 CI가 느려진다.

**무엇이며, 어떻게 해결하나?**
모노레포는 여러 앱과 공용 패키지를 하나의 저장소에서 관리하는 구조다. pnpm 워크스페이스는 로컬 패키지 연결과 의존성 관리를 돕는다. Turborepo는 작업 의존성에 맞춰 실행 순서를 정하고, 입력이 같은 작업의 결과를 캐시해 반복 실행을 줄인다. [pnpm 문서](https://pnpm.io/workspaces), [Turborepo 캐시 문서](https://turborepo.dev/docs/crafting-your-repository/caching)

**Q. 같은 저장소면 웹과 모바일 코드가 모두 공유되는가?**
실행 환경이 같아지는 것은 아니다. 타입, 검증, 계산 같은 플랫폼 독립 로직은 공유하기 쉽지만 DOM, 기기 권한, 저장소 접근은 구현을 나눠야 한다. 서비스 코드도 플랫폼 의존성을 분리해야 공유할 수 있다.

**Q. 공용 서비스에서 인증 토큰이 필요하면?**
공용 코드가 브라우저 저장소를 직접 호출하는 대신 `getAccessToken()` 같은 인터페이스를 받는다. 웹과 모바일이 각자 구현을 제공한다. 이것이 **의존성 역전과 어댑터**다. 정책은 공유하고 환경 차이는 경계 밖으로 옮긴다.

**Q. 공용화와 캐시가 항상 이득인가?**
공용 패키지에 기능을 과하게 모으면 작은 수정도 여러 앱에 영향을 준다. 공개 API와 의존 방향을 관리해야 한다. 캐시 역시 결과에 영향을 주는 파일·환경 변수 등이 입력에 포함되고 작업 결과가 재현 가능해야 믿을 수 있다.

**기억할 점:** 모노레포는 코드 관리 방식이다. 모든 앱을 함께 배포해야 한다는 뜻도, 독립 배포가 자동으로 된다는 뜻도 아니다.

## 2. Micro Frontend + Module Federation: 팀별 개발과 배포 분리

**어떤 문제가 있었나?**
여러 팀이 하나의 큰 프론트엔드를 수정하면 빌드와 릴리스 일정이 묶인다. 한 기능만 바꿔도 전체 앱의 배포를 기다리게 된다.

**무엇이며, 어떻게 해결하나?**
Micro Frontend는 업무 영역별로 프론트엔드를 나누는 아키텍처다. Module Federation은 서로 다른 빌드의 모듈을 연결하는 수단이다. Host가 전체 화면을 구성하고 Remote가 기능을 제공하는 형태가 흔하다. 실행 중 Remote를 불러오는 구성은 Host 재빌드 없이 Remote 변경을 전달할 수 있다.

**Q. 공용 패키지와 무엇이 다른가?**
일반 공용 패키지는 보통 소비 앱의 빌드에 포함되므로 변경 적용에 앱 재빌드가 필요하다. 런타임 Remote는 배포된 별도 코드를 불러온다. 대신 네트워크 로딩과 실행 시점의 호환성 문제가 추가된다.

**Q. 독립 배포인데 왜 다른 팀과 계약을 맞춰야 하나?**
props, 이벤트, 라우팅, 인증 방식이 연결 지점이기 때문이다. 기존 Host가 이해할 수 없는 Remote를 배포하면 통합이 깨진다. 하위 호환성을 유지하거나 버전을 명시적으로 선택해야 한다.

**Q. React를 각 앱에 넣으면 되는가?**
같은 화면에서 React가 중복 로드되면 Hook 등에서 문제가 생길 수 있다. `shared`와 `singleton`은 공유 범위에서 의존성 중복을 줄이지만, 버전 호환성까지 보장하지는 않는다. [Module Federation 공유 의존성 문서](https://module-federation.io/configure/shared)

**Q. Remote 장애는 자동으로 격리되는가?**
같은 페이지에서 실행되는 코드이므로 자동 격리되지 않는다. 로딩 실패 처리, 렌더 오류 경계, CSS·전역 상태 충돌 방지, 대체 화면과 롤백을 설계해야 한다.

**기억할 점:** 팀별 배포 자율성을 얻는 대신 통합 계약과 운영 복잡성을 관리한다. 작은 앱에서는 분리 비용이 더 클 수 있다.

## 3. TanStack Query: 서버 데이터의 캐시와 동기화

**어떤 문제가 있었나?**
컴포넌트마다 Effect로 API를 호출하면 로딩·오류·재시도·중복 요청·수정 후 갱신 로직이 반복된다. 같은 상품을 여러 화면에서 보여줄 때 데이터가 달라지기도 한다.

**무엇이며, 어떻게 해결하나?**
서버 상태는 서버가 원본을 소유하는 데이터다. TanStack Query는 클라이언트에 그 사본을 캐시하고 조회·재조회·변경 상태를 관리한다. 모달 열림 같은 UI 상태는 별도로 관리한다.

**Q. 같은 데이터인지는 어떻게 판단하는가?**
`queryKey`가 캐시의 식별자다.

```ts
['products', { category, page }]
```

조회 결과를 바꾸는 조건은 키에 포함해야 한다. 사용자별 데이터는 사용자 식별을 키에 반영하거나 계정 전환 시 캐시를 정리하는 등 분리 정책이 필요하다.

**Q. staleTime과 gcTime은 왜 따로 있는가?**
`staleTime`은 데이터를 신선하다고 보는 기간이고, `gcTime`은 사용하지 않는 캐시를 정리하기까지의 기간이다. 신선하지 않은 데이터도 화면에 보여주면서 재조회할 수 있다. staleTime 만료 자체가 주기적인 요청 타이머는 아니다.

**Q. 서버에서 다른 사람이 수정하면 즉시 반영되는가?**
자동 감지하지 않는다. 마운트·포커스 복귀 등의 재조회, 폴링, WebSocket 같은 전략이 필요하다. 최신성이 중요한 재고와 변경이 드문 설명 문구에는 다른 정책이 적합하다.

**Q. 저장 후 화면은 어떻게 맞추는가?**
서버 응답으로 캐시를 갱신하거나 관련 쿼리를 무효화한다. 낙관적 업데이트는 성공 전에 UI를 바꿔 반응성을 높이지만, 실패 복구와 동시 변경을 고려해야 한다. 최종 판단은 서버가 한다.

**기억할 점:** 캐시는 응답 속도와 최신성의 절충이다. Query를 도입해도 데이터의 정확성 정책은 개발자가 결정해야 한다. [TanStack Query 가이드](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

## 4. SSR·CSR·Hydration: 초기 표시와 상호작용의 균형

**어떤 문제가 있었나?**
CSR만 사용하는 화면은 JavaScript를 받은 뒤 API를 호출해야 콘텐츠가 보이는 구조가 되기 쉽다. 초기 표시가 늦어지고 검색·공유용 콘텐츠 제공도 까다로워진다.

**무엇이며, 어떻게 해결하나?**
SSR은 요청 시 서버에서 HTML을 만들어 전달한다. CSR은 클라이언트에서 화면을 구성한다. SSR은 초기 콘텐츠를 먼저 제공하고, CSR은 이후 상호작용과 화면 갱신을 담당하는 식으로 조합할 수 있다.

**Q. SSR이면 항상 빠른가?**
서버의 조회가 느리면 HTML 응답도 늦어진다. 화면이 보이는 속도와 버튼이 반응하는 속도도 다르다. LCP 같은 표시 지표와 INP 같은 반응성 지표를 함께 확인해야 한다. 변경이 드문 공개 콘텐츠는 빌드 시 HTML을 만드는 SSG도 검토할 수 있다.

**Q. Hydration이 정확히 무엇인가?**
React Hydration은 서버 HTML과 클라이언트 컴포넌트를 연결해 상호작용을 가능하게 하는 과정이다. 서버와 클라이언트의 초기 출력이 달라지면 불일치가 생긴다. 시간·난수·브라우저 저장소를 렌더 중 사용하는 것이 흔한 원인이다.

**Q. Query에서도 hydrate라는 말을 쓰는데 같은 것인가?**
목적이 다르다. Query의 hydration은 서버에서 직렬화한 캐시를 클라이언트 캐시로 복원하는 것이다. React Hydration은 UI 연결이고, Query hydration은 데이터 복원이다.

**Q. 둘을 함께 쓰면 무엇을 조심해야 하나?**
서버에서 데이터를 미리 조회하고 캐시를 전달해 클라이언트의 중복 조회를 줄인다. 적절한 staleTime이 필요하며, 서버 QueryClient는 요청별로 분리해야 한다. 브라우저로 전달하는 데이터에 서버 전용 비밀 정보가 포함되지 않도록 해야 한다. [TanStack Query SSR 문서](https://tanstack.com/query/latest/docs/framework/react/guides/ssr)

**기억할 점:** SSR 여부와 데이터 캐시 정책은 별개의 결정이다. 초기 페이지 진입과 이후 화면 전환도 나눠 평가한다.

## 5. 네이티브 + WebView: 재사용성과 기기 경험의 균형

**어떤 문제가 있었나?**
모든 기능을 플랫폼별로 구현하면 개발·수정 비용이 커진다. 반대로 모든 기능을 웹으로 만들면 기기 기능이나 플랫폼 특유의 경험을 다루기 어려울 수 있다.

**무엇이며, 어떻게 해결하나?**
WebView는 앱 안에서 웹 콘텐츠를 실행해 화면과 로직의 재사용을 돕는다. 네이티브는 기기 권한·복잡한 제스처·플랫폼 기능과 긴밀한 경험에 활용한다. 웹에서도 가능한 기능이 많으므로 실제 요구와 성능을 보고 선택한다.

**Q. WebView에서는 웹 화면만 잘 만들면 되는가?**
키보드, Safe Area, 뒤로 가기, 로그인 상태, 외부 링크와 앱 생명주기까지 확인해야 한다. 일반 브라우저에서의 정상 동작이 WebView에서의 정상 동작을 보장하지 않는다.

**Q. 웹이 네이티브 기능을 호출하려면?**
브리지 메시지로 요청한다. 메시지 타입, 요청 ID, 응답, 오류, 타임아웃을 계약으로 정의한다. 요청 ID는 동시에 실행된 호출의 응답을 올바른 요청에 연결한다.

**Q. 웹은 새 버전인데 사용자의 앱은 구버전이면?**
지원 기능이나 브리지 버전을 확인하고 대체 동작을 제공한다. 웹·앱 배포 속도가 다르므로 하위 호환성이 필요하다. 브리지는 앱 권한에 접근하는 통로이므로 출처와 입력도 검증한다. [Android WebView 브리지 문서](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)

**기억할 점:** 코드 재사용만큼 로그인·이동·오류 처리가 플랫폼 사이에서 일관되는지가 중요하다.

## 6. Mantine + 디자인 시스템: 반복되는 UI 판단 표준화

**어떤 문제가 있었나?**
팀마다 버튼·간격·오류 표시를 따로 구현하면 UI가 달라지고 유지보수가 어려워진다. 모달의 포커스 제어처럼 복잡한 동작을 매번 직접 만들기도 부담스럽다.

**무엇이며, 어떻게 해결하나?**
Mantine은 웹 UI 컴포넌트와 테마 기반을 제공한다. 자체 디자인 시스템은 이를 제품의 토큰·컴포넌트·사용 규칙으로 정리한다. theme과 Styles API로 공통 표현을 적용한다. [Mantine 테마 문서](https://mantine.dev/theming/theme-object/), [Styles API](https://mantine.dev/styles/styles-api/)

**Q. Mantine을 감싼 버튼만 만들면 충분한가?**
주요·보조 행동, 크기, 로딩, 비활성 상태, 레이블 규칙까지 정해야 한다. 디자인 시스템은 모양뿐 아니라 사용 기준을 공유한다.

**Q. 모든 경우를 지원하도록 옵션을 많이 만들면 좋은가?**
옵션이 늘면 상태 조합과 테스트 부담도 커진다. 자주 쓰는 의도를 간단하게 표현하고, 필요한 확장 지점만 제공한다. 사용 사례와 상태를 문서화하면 잘못된 사용을 줄일 수 있다.

**Q. 모바일에도 같은 컴포넌트를 쓸 수 있는가?**
WebView에서는 웹 컴포넌트를 사용할 수 있지만, React Native 같은 네이티브 UI에 Mantine 컴포넌트를 그대로 사용할 수는 없다. 색상·간격 등의 토큰과 사용 원칙은 공유하고 실제 UI는 플랫폼별로 구현할 수 있다.

**Q. 라이브러리가 접근성을 지원하면 끝인가?**
레이블 누락, 잘못된 포커스 순서, 대비 부족은 사용 단계에서 생긴다. 실제 화면에서 키보드·스크린 리더·오류 안내를 검증해야 한다.

**기억할 점:** 재사용의 단위는 컴포넌트 코드뿐 아니라 팀이 반복하는 UI 결정이다.

## 7. Mixpanel·GTM·Hackle: 행동 관측과 개선 효과 검증

**어떤 문제가 있었나?**
사용자가 어디서 이탈하는지 모르거나, 기능 변경 후 지표가 좋아져도 그 변경 때문인지 판단하기 어렵다.

**무엇이며, 어떻게 해결하나?**

| 도구 | 해결하는 문제 | 해결 방식 |
|---|---|---|
| Mixpanel | 사용 흐름과 이탈 위치가 보이지 않음 | 이벤트 기반 퍼널·리텐션 분석 |
| GTM | 분석·마케팅 태그 설정을 매번 코드 배포로 변경함 | 태그·트리거·변수 설정 관리 |
| Hackle | 변경 효과를 단순 전후 비교로 판단함 | 사용자군을 나눠 A/B 실험 운영 |

GTM의 dataLayer는 앱의 의미 있는 이벤트와 변수를 태그에 전달하는 접점이다. 새로운 이벤트에 필요한 데이터는 여전히 앱 코드에서 제공해야 할 수 있다. [Google dataLayer 문서](https://developers.google.com/tag-platform/tag-manager/datalayer)

**Q. 클릭을 많이 수집하면 좋은 분석이 가능한가?**
먼저 이벤트 이름, 발생 조건, 속성, 사용자 식별 기준을 정의해야 한다. 웹과 네이티브가 같은 행동을 중복 전송하면 지표가 부풀려진다. 로그인 전후 연결과 로그아웃 처리도 확인한다.

**Q. 결제 버튼 클릭을 구매 성공으로 보면 되는가?**
클릭은 의도다. 결제 성공은 서버의 확정된 결과를 기준으로 측정하고, 주문 ID 등으로 중복을 방지한다. 퍼널은 화면 조회 → 결제 시작 → 결제 성공처럼 의미가 다른 단계로 나눈다.

**Q. A/B 테스트에서 B의 전환율이 높으면 승자인가?**
무작위 배정, 일관된 사용자 식별, 충분한 표본, 사전에 정한 지표와 분석 기준이 필요하다. 표본 변동만으로 차이가 생길 수 있고, 결과를 반복 확인하다 유리한 순간에 종료하면 오판할 수 있다. 사용자 식별 기준은 웹·앱에서도 맞춰야 한다. [Hackle 식별자 가이드](https://hackle.io/ko/post/conquering-abtest-4/)

**Q. 실험군 배정과 실제 노출은 왜 구분하는가?**
배정된 사용자가 변경 화면을 보지 않을 수 있기 때문이다. 무엇을 노출로 볼지 사전에 정하고, 분석 대상 선택으로 실험군의 비교 가능성이 깨지지 않도록 한다.

**Q. 주 지표만 좋아지면 되는가?**
전환율과 함께 오류율·취소율·응답 속도 같은 보호 지표를 본다. 실험은 인과관계 판단을 돕지만 잘못된 이벤트나 배정 문제까지 자동 해결하지 않는다.

**기억할 점:** 이벤트는 행동을 관측하고, 실험은 변경 효과를 검증한다. 데이터 정의가 틀리면 도구가 좋아도 결론은 틀린다.

## 8. 함께 알아야 할 기본기

| 기본기 | 위 업무에서 필요한 이유 |
|---|---|
| JavaScript 비동기·이벤트 루프 | 요청 순서, 응답 경합, 브리지 통신과 UI 멈춤 이해 |
| TypeScript와 런타임 검증 | 공용 계약 표현 및 외부 API·메시지 입력 검증 |
| React 렌더·Effect·정리 함수 | 중복 요청·구독 누수·분석 이벤트 중복 방지 |
| HTTP 캐시·쿠키·CORS·CSP | 인증, 리소스 로딩, 출처 정책과 캐시 문제 해결 |
| 접근성·반응형·크로스 브라우징 | 브라우저·기기·WebView별 사용 가능성 검증 |
| CI/CD·관측·롤백 | 독립 배포 이후의 장애 탐지와 복구 |

TypeScript 타입은 실행 시 API 데이터를 검증하지 않는다. CORS는 브라우저의 교차 출처 응답 접근 정책이며 사용자 인증을 대신하지 않는다.

## 9. 개념을 연결하는 실무 예시: 상품 구매 화면 변경

1. **공용 패키지:** 가격 계산과 입력 검증을 공유하되 플랫폼 저장소 구현은 분리한다.
2. **Module Federation:** 구매 기능을 배포하면서 기존 Host와의 계약 호환성을 유지한다.
3. **SSR + Query:** 공개 상품 정보를 먼저 표시하고 재고는 필요한 최신성 정책으로 재조회한다. 주문 확정 시 서버가 재고를 다시 검증한다.
4. **네이티브 + WebView:** 웹 구매 화면에서 기기 기능이 필요하면 지원되는 브리지로 요청한다.
5. **디자인 시스템:** 구매 버튼의 로딩·중복 제출 방지·오류 안내를 일관되게 구현한다.
6. **분석 + 실험:** 구매 시작과 성공을 구분하고, 변경 효과를 전환율과 오류율로 검증한다.

각 기술의 가치는 “무엇을 썼는가”보다 “어떤 문제를 줄였고, 어떤 책임이 여전히 남는가”로 설명할 수 있어야 한다.
